# 诊断协议（Diagnosis Protocol）

> 诊断的目标不是"找出所有问题"，而是**找出最值得修的三个**。
> 顺序不能乱：先结构（灰度/分组/层级/对齐），后皮肤（对比度/触控/动效）。

---

## 一、灰度测试（结构是否成立的第一道闸）

**操作步骤（必须照做，不能凭感觉）**
1. 截整屏图（1440×900 或 390×844），不要裁切
2. 去色（图像软件"黑白"或 CSS `filter:grayscale(1)`）
3. 缩小到原尺寸 25%（这一步会干掉细节，只留结构）
4. 看 3 秒，回答三个问题：
   - 第一眼看到什么？
   - 第二眼去哪？
   - 知道下一步做什么吗？
5. 如果答不出"先看哪 → 再看哪"，**结构不成立**，禁止进入配色讨论

**判定**
| 结果 | 结论 | 允许的干预层级 |
|---|---|---|
| 3 秒能说出焦点与顺序 | 结构成立 | token 级 / 组件级 |
| 能看出焦点但顺序混乱 | 结构部分成立 | 组件级（重排组内） |
| 看不出焦点 / 一片平 | 结构不成立 | 结构级（换骨架） |

## 二、七项扫描表

### 1. 灰度与层级
| 项 | 怎么测 | 通过标准 | 常见问题 |
|---|---|---|---|
| 焦点数量 | 眯眼/模糊截图 | 恰好 1 个 | 3 个同级大标题 |
| 层级依据 | 去色后看 | 靠尺寸/对比/位置成立 | 只靠颜色区分主次 |
| 阅读顺序 | 25% 缩略图 | 有明确 Z 或 F 型路径 | 视线来回跳 |

**处方**：主标题放大到次标题的 ≥1.5 倍；删掉次级元素的高饱和色；把次要块降为 caption 档。

### 2. 分组（格式塔）
| 项 | 怎么测 | 通过标准 | 常见问题 |
|---|---|---|---|
| 内部 ≤ 外部间距 | 量卡内 padding vs 卡间距 | 内 ≤ 外（建议内 20、外 32） | 卡内 28、卡间 16 → 分组崩塌 |
| 相似性 | 找同类元素 | 同功能同外观 | 两个"保存"不同尺寸/颜色 |
| 闭合 | 数边框数量 | 用留白就能分组 | 每块都 1px 描边，像表格 |
| 连续 | 画对齐线 | 同列一条线 | 左边缘 2-4px 参差 |

**处方**：先调间距（最便宜），再删描边，最后才考虑加容器。

### 3. 对齐
| 项 | 怎么测 | 通过标准 |
|---|---|---|
| 列对齐 | DevTools 量 left 值 | 误差 ≤1px |
| 数字对齐 | 看右边缘 | 右对齐 + 等宽 |
| 图标文字 | 看基线 | 基线对齐（非外框） |
| 卡片等高 | 看底边 | 同一行等高（用 `align-items:stretch`） |

### 4. 对比度
```bash
python scripts/audit_contrast.py <页面>.html
```
| 对象 | 阈值 |
|---|---|
| 正文 | 4.5:1 |
| 大字（≥24 / ≥18.66 粗） | 3:1 |
| 图标/边框/焦点环 | 3:1 |

**处方**：不是"整体调亮/调暗"，而是只调不达标的那一对；优先调文字色，不动背景（背景牵一发动全身）。

### 5. 触控与可达
| 项 | 通过标准 | 常见问题 |
|---|---|---|
| 触控目标 | ≥44×44（紧凑 ≥40） | 图标按钮 24px |
| 焦点环 | 可见 2px + offset | `outline:none` 未补 |
| 键盘顺序 | Tab 逻辑顺序 | 视觉顺序与 DOM 顺序不一致 |
| 输入字号 | ≥16px | 14px 导致 iOS 缩放 |

### 6. 密度
| 项 | 通过标准 |
|---|---|
| 模式一致性 | 全页舒适 或 全页紧凑，不混用 |
| 紧凑理由 | 有（≥3 列、≥20 行、日用时 ≥2h） |
| 空域 | ≥35%（营销页）、≥25%（后台） |

### 7. 动效必要性
对每个动效问三句：
1. 它属于五类中的哪一类？
2. 去掉它，用户会误解什么？
3. 时长是否在区间内？

三句有一句答不出 → 列"待删"。

## 三、处方库（按症状查）

| 症状 | 根因（最可能） | 第一处方 | 第二处方 |
|---|---|---|---|
| "太挤了" | 间距系统缺失 | 卡内 20→28、卡间 16→24 | 密度降一档（行高 +8） |
| "太土了" | 饱和度低 + 色相多 | 饱和度 +20%、色相收敛到 ≤2 | 换中性阶（带轻微色相） |
| "太花" | 强调色超预算 | 强调色压到 ≤5 处 | 删渐变与阴影层级 |
| "没重点" | 层级只靠颜色 | 字号拉开 1.5 倍 | 删掉次级的彩色 |
| "字看不清" | 对比度或字号不足 | 调深文字色一档 | 正文 ≥16px、行高 1.6 |
| "像表格" | 到处描边 | 删 80% 的 1px 边框 | 用留白 + 底色分组 |
| "不像大厂" | 网格不严谨 | 8pt 网格 + 数字等宽 | 统一圆角分级 |
| "太像 AI 做的" | 命中反模式组合 | 对照 `anti-patterns.md` 逐条排 | 换一个签名手法 |
| "操作太麻烦" | 路径过长 | 合并步骤 / 预填 | 高频项提到一级 |
| "不知道点了没" | 状态缺失 | 补 hover/active/loading | 加成功反馈 + aria-live |

## 四、优先级打分（把争论变成算术）

```
优先级分 = 影响人数(0-3) × 成本等级(1-3) ÷ 修复成本(1-3)
```

| 分值 | 处理 |
|---|---|
| ≥6 | 必修（本轮） |
| 3-5.9 | 应修（本轮或下轮） |
| <3 | 可延（记录，不承诺） |

**影响人数**：所有人=3、多数=2、少数=1、极少数=0.5
**成本等级**：认知/操作/时间=1，错误=2，信任=3（信任问题最难挽回）
**修复成本**：改 token=1、改组件=2、改结构=3

示例：次要文字对比度不足 → 3×1÷1 = **3.0**（应修，但便宜，顺手做）
示例：核心任务 4 步 → 3×2÷2 = **3.0**；若改结构 3×2÷3 = **2.0**（可延）

> 注意：分值只用于排序，不用于"是否值得做"的最终判断——信任类问题即使分值低也应优先。

## 五、诊断报告模板（可直接套）

```markdown
# 诊断：{页面名}

## 结论（一句话）
{结构成立 / 结构不成立}；主要问题是 {X}，次要 {Y}；建议 {干预层级}。

## 必修
| 问题 | 证据 | 成本类型 | 处方 | 优先级 |
|---|---|---|---|---|
| 卡内 28 > 卡间 16，分组崩塌 | 量得 | 认知 | 内 20 / 外 32 | 9.0 |

## 应修
...

## 可延
...

## 明确不改
- {某元素} 保持原样，因为 {它的对比是刻意的/用户已形成肌肉记忆/改造成本 > 收益}

## 灰度测试记录
去色 25% 截图：能看出 {焦点}，阅读顺序 {A→B→C}，判定 {通过/不通过}。
```
