# 需求澄清与迭代流程（Intake → Spec → Preview → Iterate）

> 目的：避免"没问清楚就开做"和"改到第 8 版还不对"。
> 每次接到 UI 需求，按本流程执行；**每一步都有交付物，不能跳步**。

---

## 第 1 步 · Intake（先问三件事）

### 1.1 三个必问问题

```
1. 给谁用？（用户画像：角色 / 年龄层 / 使用频率 / 设备）
2. 他们来这一屏要完成什么？（唯一核心任务）
3. 什么场景下用？（时间/地点/光线/单手还是桌面/网络条件）
```

**问法纪律**：一次性问完，不要挤牙膏；用户说不清就给选项（"更像 A 还是 B"）。
问题不超过 3 个，其余靠行业默认值推断并在方案里标注。

### 1.2 行业默认推断表（用户没说时用，必须在方案里注明"按行业惯例推断"）

| 行业 / 场景 | 画像默认 | 骨架默认 | 动效默认 | 密度 |
|---|---|---|---|---|
| 工厂 / 点检 / 监控 | 一线操作员，中年，长时间 | 侧栏 + 6-8 KPI + 告警列表 | B 端低动效 6-8s | 高 |
| 企业 SaaS 后台 | 运营/管理员，全天 | 侧栏 + 4 KPI + 表格 | B 端低动效 | 中高 |
| 电商 C 端 | 消费者，碎片时间 | 渐变头 + 宫格 + 商品流 + 吸底 | C 端柔和 3-4s | 中 |
| 政务 / 民生 | 居民，低频、强指引 | 渐变头 + 大图标宫格 + 办理入口 | 轻（≤0.3s） | 低中 |
| 文旅 / 酒店 | 游客，决策期、看图 | 全屏实景 + 玻璃条 + 榜单 | C 端柔和 | 低 |
| 医疗 / 教育 | 患者/家长，焦虑、需信任 | Hero 问候 + 时间轴 + 主从双栏 | 克制 | 中 |
| 数据大屏 | 指挥/参观，远距离 | 中心 3D + 环绕面板 | 流光 3-5s | 高 |

### 1.3 输出：需求卡（5 行）

```markdown
- 画像：{角色}，{年龄段}，{设备}，{使用频率}
- 核心任务：{一句话，动词开头}
- 场景：{环境 + 约束，如"车间强光下扫码"、"地铁单手" }
- 成功标准：{可验证，如"3 秒找到今日待办" }
- 明确不要：{用户提到的排除项}
```

## 第 2 步 · Spec（先出方案，不写代码）

### 2.1 五段式方案卡

```markdown
## 设计方向：{一句有主张的话，例如"暖白纸感 + 单一陶土色 CTA"}

### 配色
主色 {#hex}（用途）｜ 中性阶 {bg/surface/ink/ink-2/ink-3} ｜ 语义 {成功/警告/危险}
强调色预算：{3-5} 处 ｜ 趋势色约定：{红涨 / 绿涨}

### 布局（骨架）
{骨架名}：{侧栏宽} + {顶栏高} + {内容分栏}；关键屏 {3 个}

### 排版
Display {px}/{weight} · 区块标题 {px} · 正文 {px}/{行高} · 元信息 {px}
字号跨度 {倍数} ｜ 字重 {≤3 种} ｜ 中文行宽 {字符数}

### 动效
MOTION 旋钮 {1-10}：入场 {时长/缓动} ｜ 交互 {时长} ｜ 呼吸 {周期/振幅/数量}

### 交互
每个可点元素 8 态；主操作成功动画 {有/无}；模块聚焦 {有/无}；
关键状态：{空/加载/错误/成功，各自怎么表现}

### 风险与取舍
{例如：图表用内联 SVG 而非 Chart.js，牺牲交互换取零依赖}
```

### 2.2 方案自检（出方案前过一遍）

```
[ ] 骨架是否对应"端 + 行业"（见 intake 推断表）
[ ] 是否有一个主角（数字/标题/图片），不是平均用力
[ ] 配色是否 60-30-10，强调色 ≤5 处
[ ] 字号是否 ≥3 档且跨度 ≥2.4 倍
[ ] 动效是否说明"解决什么问题"，而不是"加了什么效果"
[ ] 是否列出了"明确不做"的部分
```

## 第 3 步 · Preview（先给能点的东西，不给形容词）

### 3.1 交付内容

1. **3 个关键屏**（不是全部页面）：首屏 / 主任务流的一屏 / 一个状态屏（空或错误）
2. **单文件 HTML**，双击可看；含浅/深两套令牌与 reduced-motion
3. **一页说明**：用法（点哪里）、已知取舍、下一步建议

### 3.2 预览必须能验证的四件事

| 要验证的 | 怎么看 |
|---|---|
| 3 秒可读 | 打开首屏，计时 3 秒后问"这是什么、能干什么" |
| 层级 | 眯眼截图，是否只有一个焦点 |
| 对比度 | `audit_contrast.py` 0 违规 |
| 交互 | 每个按钮点一遍，是否有反馈；模块聚焦是否可 Esc 恢复 |

## 第 4 步 · Iterate（不满意时，先归类再改）

### 4.1 反馈四分类 → 参数动作（**禁止整页重做**）

| 用户说 | 真实类别 | 对应动作（只动这些） |
|---|---|---|
| "感觉不对 / 不是我想要的" | **结构** | 换骨架（按 intake 表），保留配色与文案 |
| "不好看 / 有点土" | **视觉** | 降饱和 20%、收敛色相 ≤2、强调色压到 ≤5 处、提升字号跨度 |
| "太挤 / 太空" | **密度** | DENSITY ±2；卡内边距 20→28；区块间距 ±30% |
| "没反应 / 不知道点了没" | **反馈** | 补 8 态 + 成功动画 + `aria-live`；按钮宽度锁定 |
| "字看不清" | **可读性** | 调深 ink 档位、提字号、加 scrim（先跑审计） |
| "太花 / 太吵" | **动效/装饰** | MOTION -2；呼吸元素减到 ≤1；删渐变与发光 |

### 4.2 迭代纪律

```
单轮只改一类问题（结构 / 视觉 / 密度 / 反馈 之一）
每轮必须给"改前 / 改后"对照（同尺寸截图或同屏 HTML）
最多 3 轮；第 3 轮仍不满意 → 回到第 1 步重问画像与场景，而不是继续微调
每轮结束写一行迭代记录（见 4.3）
```

### 4.3 迭代记录模板（附在交付里）

```markdown
| 轮次 | 用户反馈原话 | 归类 | 改动参数 | 结果 |
|---|---|---|---|---|
| 1 | "太挤了" | 密度 | DENSITY 7→4；卡内边距 20→28 | 通过 |
| 2 | "按钮点了没感觉" | 反馈 | 加 8 态 + 成功动画 220ms 勾线 | 通过 |
```

## 第 5 步 · 沉淀（把这次的结论变成下次的默认）

| 情况 | 动作 |
|---|---|
| 某个参数被验证有效（≥1 次） | 建 `P` 卡或 `M` 卡，`confidence: 1`，写清适用端与行业 |
| 累到 3 次独立验证 | `kb.py promote` → 置信 3，进入默认检索 |
| 某个做法被否掉 | 建 `A` 卡（反例 + 替代方案） |
| 某个判断反复出现 | 建 `J` 卡（什么场景选什么） |
| 用户个人偏好（颜色/字号/语气） | 写进项目 `DESIGN.md`，不要污染通用知识库 |

```bash
python scripts/rag.py index                 # 重建检索索引
python scripts/kb.py add 新卡片.md          # 校验入库
python scripts/kb.py index                  # 更新知识索引
```

---

## 一页速查

```
问 3 件事 → 出一页方案 → 给 3 屏可点的预览 → 反馈归类改一类 → ≤3 轮 → 写 1-3 张卡
```

**最容易犯的三个错**：
1. 没问场景就选骨架（结果"好看但用不了"）
2. 用户说"不好看"就整页重做（应该先归到视觉/密度/结构之一）
3. 改完不记录（下次从零开始，能力不增长）
