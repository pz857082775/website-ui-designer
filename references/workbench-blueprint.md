# 工作台蓝图（Workbench Blueprint）

> 整合自 `mouse-lin/finesse-brief`（skills/finesse-brief，MIT）。
> 解决的问题：**工作台最容易做成"功能菜单 + 一堆漂亮但没用的数字"**。
> 这个蓝图规定了建造顺序，以及一条不可跳过的闸门：**数据地板**。

---

## 一、五个部件，顺序不能换

| # | 部件 | 回答什么问题 | 何时建 |
|---|---|---|---|
| 1 | **身份**（名字 + 给谁用 + 围绕什么对象） | 这是谁的台子？围着什么转？ | 最先 |
| 2 | **钩子**（打开时看到的那句话/结论条） | 打开它，跟我说什么？ | **第二，先于模块** |
| 3 | **数据地板**（那句话下面的字段与写入者） | 这句话凭什么成立？ | 第三，且是闸门 |
| 4 | **模块**（侧栏/页面/实体） | 我还能在这儿干什么？ | 第四 |
| 5 | **收入缝**（钱可以从哪冒出来） | 它靠什么活？ | 最后，且从已有模块里长出来 |

**为什么顺序重要**
从模块清单开始（最自然的冲动，因为模块好玩）→ 会做成"功能菜单"，再反推一个能罩住整个菜单的钩子 → 那个钩子必然是泛的。
**正确的做法**：先写他打开时看到的那句话，模块是"为了让这句话持续成立而必须存在的东西"。

### 1.1 身份行是承重结构，不是装饰

「小暖的姨妈工作台」>「经期管理系统」——前者锁定了范围（一个人、一个周期、一个要通知的伴侣）。

**系统型工作台要命名"主语"**：
「围着客户转」与「围着订单转」会产出完全不同的 CRM——一个是关系历史，一个是履约队列。
**命名了名词，模块会自己长出来**；没命名，两种都做不好。

## 二、数据地板（唯一不可跳过的闸门）

对钩子的**每一个从句**、以及每个声称展示"今天的"模块，回答五个问题：

| # | 问题 | 什么情况下算失败 |
|---|---|---|
| 1 | 它读哪个字段？ | 这句话需要没人定义过的数据 |
| 2 | 谁/什么写入这个字段？ | 见第三节——"用户会填"在系统型里往往是错的答案 |
| 3 | 什么时候写？ | 一天里没有任何时刻会发生 |
| 4 | 第一天是空的，它显示什么？ | 空白、`--`、0 行表格，或者一句谎 |
| 5 | 某天没记录 / 数据源断了？ | 静默把旧数据当新数据展示 |

### 2.1 幸运饼干测试（Fortune-cookie test）

把钩子当成 **第 40 天、什么都没记录、任务也没跑** 的样子读一遍。
如果它读起来和第 1 天一模一样，那它不是钩子，只是恰好在页面顶部的装饰。

```
今天是黄体期第 3 天 · 今日 3 件小事
  需要：周期开始日（用户，每月一次）  第一天：先记一下上次月经开始那天

今天推日 6 组 · 蛋白缺口 42g
  需要：分化计划（由星期推导，免费）+ 今日摄入（用户，每餐后，昂贵）

12 个商机待跟进 · 3 个超 7 天没动
  需要：opportunity.stage + last_activity_at
  写入：销售改阶段时 / 系统写跟进记录时自动落
  第一天：还没有商机 —— 导一份客户名单，或先建一个

4 个在跑 · 1 个昨晚失败 · 本月 ¥320
  需要：run.status（系统，每次运行落一条）+ usage（集成回传）
  第一天：先建第一个 Agent，跑完这儿就有数了

今天也要加油哦 ✨            → 不需要任何数据，因此什么也没说，禁用
共 1,284 个客户 · 系统运行正常  → 一个常量 + 一句同义反复，也禁用
```

**两条禁令**
1. **没有变量的钩子，直接禁用**——它在定义时读起来很顺，所以最难发现
2. **系统型特有的版本：由总数构成的钩子**（"共 1,284 个客户 · 本月新增 32"）——技术上会变，但不告诉他今天该干什么。
   **结论条里必须至少有一个从句指向"今天要处理的事"**：待跟进 / 超期 / 失败 / 告警 / 缺货 / 待审；否则它只是统计条。

### 2.2 字段需要他不会给的输入时，四个动作（按顺序）

1. **推导**：星期 → 推日/拉日；一个考试日期 → 距离天数；支付回调 → 订单状态；`last_activity_at` + now → 超期
2. **只问一次**：周期开始日、宠物生日、考试日、月度目标、告警阈值
3. **把日常输入变成一次点击**：默认"与昨天相同"；看板卡拖一列
4. **改钩子**，换成现有数据能支撑的那句——**诚实地缩小，是成功不是妥协**

### 2.3 四类写入者（系统型最容易搞错的地方）

| 写入者 | 含义 | 成本 | 陷阱 |
|---|---|---|---|
| `user` | 人打字或点击 | **规格里最贵的东西** | 每个模块给三个字段 = 悄悄造了一份全职录入工作。数一数 |
| `system` | 工作台自己作为动作的副产物写入（跑完 → 一条 Run；拖阶段 → `last_activity_at`） | 免费 | **优先找这类** |
| `integration` | 别的系统提供（支付回调、模型用量、设备上报、ERP 同步） | **只有集成真的建了，字段才存在** | 系统规格里最常见的谎："数据从 ERP 来"，但没有 ERP、没有 API、没有计划 |
| `derived` | 读取时由其他字段算出（超期 = now − last_activity_at > 7d） | 免费 | 只跟输入一样真；输入来自未建集成，它就是虚构的 |

**规则**：钩子里每个字段都要标注写入者；**凡 `integration` 字段，必须写清来源系统以及它今天是否存在**。
一个结论条依赖三个未建集成的规格，就是一份"上线即空白"的规格——这正是这套方法要防的失败。

## 三、时刻（Cadence & the Moment）

工作台是在**某个时刻**被打开的，不是"有空的时候"。命名它：
`早上通勤 · 睡前 · 练完那一下 · 收摊后 · 上班坐下第一件事 · 交接班时 · 周一晨会前 · 出报表那天`

**时刻决定三件事**
- 钩子的时态（早晨是命令式"今天该做什么"，晚上是回顾式）
- 输入的可承受体量（没人会在 23:50 填一张表单）
- 在纯网页里（没有推送）——**有没有任何东西把他带回来**

**没有命名的时刻，就没有节奏**，只会因为好奇被打开两次。
网页版比 App 更需要这条：App 可以用通知补一个弱时刻，浏览器标签页不能。
**如果他的一天里没有这个时刻，工作台不会创造它**——要么依附到他已经在做的事上，要么诚实地降低频率，按"每周"设计。

---

## 四、结构与交接

- **结构由类别决定，不由用户画像决定**：任务台 / 关系台 / 履约台 / 内容台 / 监控台，五类骨架不同（侧栏组合、钩子形态、行结构都不同）
- **领域黑名单**：每个领域都有一份"这个领域最容易做烂的三件事"清单，建之前先跑一遍
- **交接即停止**：写一份规格（身份行 / 钩子 / 数据地板表 / 模块 / 空态文案 / 时刻 / 收入缝），**然后停手**。
  不要顺手把页面也写了——那会让规格失去约束力

## 五、工作台自检（在写任何代码前）

```
[ ] 身份行命名了主语（围着什么转），不是"XX 管理系统"
[ ] 钩子先于模块写完，且能被独立评审
[ ] 钩子里每个字段都标了写入者；integration 字段标了"今天是否存在"
[ ] 五个问题（字段/写入/时机/第一天/断源）全部有答案
[ ] 幸运饼干测试通过：第 40 天空数据时读起来仍然成立且有行动指向
[ ] 钩子至少一个从句指向"今天要处理的事"
[ ] 命名了打开时刻；若无此时刻，已诚实降频
[ ] 用户填写字段数量已清点，且没有把三个字段/模块派给 user
[ ] 空态文案写好了（不是"暂无数据"四个字）
[ ] 写的是规格，不是页面
```
