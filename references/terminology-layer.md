# 说法层（Terminology Layer）

> 整合自 `mouse-lin/finesse-term`（MIT，内置 142 条术语库，五册：web/h5/motion/mp/base）。
> 解决的问题：**用户描述的是症状，术语描述的是成因**。
> "按钮被底下那条黑杠挡住了" → 安全区。这个翻译是用户自己做不到、而每一轮都需要的那一步。

---

## 一、什么时候用

用户用大白话描述了界面的效果、交互、状态、动效、质感或故障时：

```
"鼠标放上去变个色"      "点了没反应"          "底下那条黑杠挡住按钮了"
"弹窗底下还能滑"        "键盘把输入框挡住了"  "内容太长省略一下"
"看着有点土"            "太挤了不透气"        "一条数据都没有的时候"
"图片加载完页面往下跳"  "在微信里打开显示不对"
```

反向场景：用户贴了别人（Agent / 同事）的话看不懂时（"他说要做乐观更新和错误回滚""他说这里 CLS 有问题"），
挑出**最影响下一步判断**的那一个概念解释。

---

## 二、三条硬门禁（违反即变成炫技）

### 门禁一 · 指得出触发的那几个字
每条术语必须能指着用户**这一轮的原话**说出是哪几个字触发的。指不出来 → 不提。
宁可一条都不提。**用户表达已经准确时，沉默是正确输出。**

### 门禁二 · 成对的坑必须一起给
移动端的坑几乎都是成对的，只给一半等于埋雷：

| 只说了这个 | 必须一起说 | 否则 |
|---|---|---|
| 吸底操作栏 | **安全区** | 全面屏上按钮被 Home 条压掉一半 |
| 弹层 / 底部弹层 | **滚动穿透（滚动锁）** | 弹窗底下页面跟着滑，关掉还弹回顶部 |
| 输入框 / 表单 | **键盘顶起** | iOS 上键盘把提交按钮顶出屏幕 |
| 图片 / 封面 | **宽高比容器** | 图一加载完，正要点的按钮跑了 |
| 头尾固定 | **滚动容器** | iOS 地址栏一收缩，固定栏开始抖 |

### 门禁三 · 结果在前，术语在后
先干完活，再在结果里带一句术语。**一次最多 1-3 条**，只提最有帮助的那条。
不生成学习路线、课程、练习、术语清单——用户没要。

---

## 三、怎么查（有库就查，别凭印象）

```bash
node "<skill-root>/scripts/term.mjs" find --q "底部按钮被那条黑杠挡住了"
```

- **按子句拆开查**，不要整句丢进去：一句话里常有两三件事
- `--q` 最多 5 次；已知场景时用 `--surface web|h5` 限噪
- 返回 `count: 0` 是**正常结果**，不是失败——说明这轮不值得提术语，按门禁一保持沉默
- **只使用检索器返回的内容**；库里没有的，就照常用大白话说清楚，别包装成术语

**没有 Node / 执行不了时**：直接读 `<skill-root>/data/*.json`，拿原话去对 `trigger` 与 `aliases` 字段；
门禁一的证据就是"对上的那条 trigger"。**不要凭印象补。**

## 四、词条结构（三个字段决定它有用）

| 字段 | 是什么 | 为什么重要 |
|---|---|---|
| `trigger` | **用户会怎么描述这件事**（不是它叫什么） | 检索主键；说不出名字正是要解决的问题 |
| `say` | 可直接复制给 Agent 的一句标准表达 | 让"改成准确需求"这件事一键完成 |
| `trap` | 这个术语最常见的翻车方式 | **多数时候比定义更值得说** |

## 五、输出形态（三种场景，各有模板）

### 5.1 做任务时（最常见）
先干完，再在结果里带一句。术语第一次出现用「大白话（术语）」：

```
已给下载按钮加了文字提示（Tooltip）：悬停或键盘聚焦时显示「下载」。
另外把底部操作栏的内边距接上了安全区（Safe Area），否则全面屏上会被 Home 条压住一半。
```

不要单独开"术语科普"段落、不要用列表罗列、不要解释你为什么要说这个。

### 5.2 改写需求时（用户要发给别人）
先给可直接复制的那一段，再补术语：

```
可以直接这样说：

「为按钮补充 Hover 状态与 Active 状态，并用 150ms 过渡让状态变化更自然。」

术语提示：
- Hover / Active：鼠标停住与手指按下时的两种样子，手机上只有后者，所以两个要一起做。
```

**保留原意、语气和约束**：用户没说要 Vue，改写后就不该出现 Vue。优先写**可观察的行为与结果**。

### 5.3 解释别人的话时
只讲三件事：在当前任务里具体指什么、它负责什么、一个容易混淆的边界。不逐词翻译，不顺势开课。

## 六、说法对齐表（可选产出）

同一个组件在需求、代码、沟通里有三种叫法时（"弹窗/浮层/模态框"），写一张表钉死：

```markdown
# 说法对齐表

| 本项目统一叫 | 术语 | 代码里的名字 | 别再叫 |
|---|---|---|---|
| 底部弹层 | Bottom Sheet | `<BottomSheet>` | 半屏弹窗 · 上拉框 · 抽屉 |
| 空状态 | Empty State | `<EmptyState>` | 缺省页 · 无数据页 |
| 骨架屏 | Skeleton | `<Skeleton>` | 占位图 · loading 页 |
```

只在用户要求，或同一概念出现第三种叫法时才写。没有文件系统时，把表打印在可复制的代码块里，不要假装写了文件。

## 七、与设计流程的接法

```
需求澄清（A-1）→ 说法层把"用户原话"转成"可执行描述" → 方案卡 → 交付
                                                          ↓
                                              交付时用「大白话（术语）」带 1-3 条
```

**边界**：说法层只决定"这件事该怎么说"，不决定做什么、也不决定好不好看。
设计执行仍由主流程与项目规范决定；不要因为用户说了"苹果风"就自动匹配 Bento / 玻璃 / 3D。

---

## 八、范围之外

- 后端、数据库、部署、构建工具的术语（只管看得见的那一层）
- 教学：不生成学习路线、课程、背诵清单
- 对已经准确的话做修饰——**"不用说"是最常见的正确输出**
